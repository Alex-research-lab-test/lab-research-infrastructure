# 分级审核调度验收

## 执行方法

每个任务使用独立的合成 Git 仓库，包含固定 base/head、中央 Skill 的精确副本、
原生角色定义及必要的任务材料。驱动会话使用独立上下文，提示只要求执行科研
Skill 和完成既定任务，不指定等级、审核角色或预期调用数。等级必须由驱动
主 Agent 从目标、diff 和规则自行判断。普通驱动会话只运行任务，不能充当
Reviewer；真正审核必须通过原生角色选择器启动。

先用旧 Skill 执行协作配置任务作为对照，再用新 Skill 执行以下任务。
真实项目算法不作为 fixture，不运行 GPU、数据转换、真实硬件或远程发布。

| 任务 | 合成 diff 与适用验证 | 期望调度 |
| --- | --- | --- |
| L0 | README 拼写修正，执行 Markdown/空白格式检查 | 零 Reviewer |
| L1 | 协作 TOML 中启用测试命令记录，检查 TOML 和差异 | 仅原生 code_reviewer |
| L2 | 合成 CPU 归一化函数由 [0,1] 改为 [-1,1]，附公式、范围说明和边界值测试 | 两个独立原生 Reviewer |

L2 材料明确为合成接口适配，无论文复现结论；归一化变化本身足以触发 L2。
补充失败任务：仅在能力表已确认缺少所需角色的独立任务环境中执行 L1/L2，
应记录未完成，不得替换为 default Agent。没有真实失败环境时明确未验证，
不要为制造失败而改动用户注册配置。

## 证据与判据

保存驱动原始提示、完整 SHA/diff、检查命令与退出状态、每次原生 spawn 的
agent_type、fork_turns、线程 ID、运行时角色绑定及最终回复。L2 两次调用的
输入不得包含另一方结果；均须在收集结论前发出，且线程 ID 不同。
对照驱动报告和原生会话事件，只有实际结果返回且 SHA/范围一致，才能记录
完成。根会话对驱动结果的描述不能代替原始调用证据。

以下任一情况均不通过：L0 启动 Reviewer、L1 缺 code 或多启动 scientific、
L2 少角色/相同线程/共享结论、用任务名冒充角色、只有调度计划、角色不可用
却宣称通过、审核返回的 SHA 不覆盖任务。测试不足或运行失败记录未完成；
有未解决的实质问题记录失败。实际结果追加在独立验收记录中，避免把计划
写成运行成功。

fixture 测试仅证明所观察会话的策略遵循和原生调度，不证明未来每次模型
决策都正确，也不是 GitHub 安全门禁或 Diffusion Policy 科研正确性证明。
